# Kotoba の表現力、ライスの定理、安全境界

状態: 2026年10月23日に確認した設計解説。[英語の正本](computability-and-safety.md)。
この文書は言語の意味を変更せず、runtime の新しい実行保証を与えるものでもない。
短い紹介は[日本語・英語の blog 原稿](../../site/computability-article.edn)に記録する。

Kotoba は、高水準のプログラミング表現と、明示的な effect・権限境界を組み合わせる。
コンポーネントの検査を通過したという事実だけから、任意の意味的正しさ、プログラム同士の
意味的同値性、すべての入力での正常終了を導くことはできない。

| 問い | Kotoba の対応 | 保証の範囲 |
|---|---|---|
| 有用な計算を書きやすいか | コレクション、レコード、関数、既存プリミティブへの展開 | 実際のアプリの記述・保守で評価する |
| どの effect が必要になり得るか | 閉じた呼び出しグラフ上の保守的な伝播 | 各実行で本当に起きる操作を完全に予測するものではない |
| この操作を今実行してよいか | コンパイラの証拠、要求、委譲、方針、runtime の状態を交差 | コンパイラ・ホスト・provider の正しい実装に依存する |
| 計算が正常に完了するか | 実行プロファイルの予算とホストの停止機構 | 強制停止は正常終了の証明にはならない |
| 選択した定義・結果と同一か | 内容に基づく CID | 任意のプログラムの同値性・正しさは判定しない |

## チューリングのタール穴への対応

Perlis のいうタール穴は、「何でも計算できるが、有用なことを簡単に書けない」という
言語設計上の問題である。これは決定不能性の定理ではない。計算の万能性だけでは、
アプリを書き、理解し、保守する容易さは決まらない。

Kotoba の[文法の契約](../../lang/guest-grammar.edn)は、表現力を既存プリミティブへの展開、
または宣言された capability kit によって拡張すると定める。コレクション、分配束縛、
レコード、高階関数などを対応するプロファイルで利用できる。
小さいコアの上でも、通常のアプリを高水準のまま記述する設計である。

この方向性だけでタール穴を避けられたと証明できるわけではない。実際のアプリで必要な
回避策、診断の分かりやすさ、target の違いによる負担を評価する必要がある。
[surface status](../../lang/surface-status.edn) と
[構文レビュー](../kotoba-syntax-quality-review.md)を確認し、一つの構文があることを
すべての backend の対応と取り違えない。

## ライスの定理と検査対象

ライスの定理は、万能な計算モデルの任意のプログラムを対象にすると、その計算する
部分関数の非自明な性質を、常に停止して正しく判定するアルゴリズムは存在しないと述べる。
「非自明」とは、その性質を満たす計算関数も、満たさない計算関数も存在することをいう。

制限したプログラム集合の検査、個別の証明、保守的な解析、実行時の強制は可能である。
十分条件を検査する方式では、実際には問題なく動くプログラムを拒否することも許容する。
ソースの構文に関するすべての問いが決定不能になるわけでもない。

Kotoba の effect 推論は、直接の effect を集め、呼び出し先の capability effect を伝播して
固定点を求める。対象は受け入れた有限の呼び出しグラフと effect 集合であり、
すべての入力で到達する分岐や、任意の計算の意味を完全に求める必要はない。
局所的に処理される ability には別の規則があり、あらゆる effect を無条件に集合和する
実装ではない。

[実行時の権限契約](logic-authority.md)では、次の条件をすべて必要とする。

1. コンパイラが、その操作を静的に可能なものとして受け入れている。
2. 今回の実行が、具体的な操作を要求している。
3. 委譲された権限が、その資源と操作を含む。
4. ローカル方針が許可する。
5. provider と現在の runtime の状態が、その操作を実行可能としている。

ここを通過して初めて、ホストが具体的な capability を渡す。正しく閉じ込められた
コンポーネントに有効なネットワーク権限がなければ、この境界を経由してネットワーク
provider に到達できない。この制限の強制に、計算のあらゆる意図を理解する必要はない。
一方、許可した操作でも、目的を誤ったり有害な使い方をされたりする余地はある。
権限境界だけでユーザーの意図や業務上の正しさまで証明することはできない。

[安全性の主張](../../lang/safety-claims.edn)は、信頼する実装と残余リスクを明記している。
解析・binding・資源 scope の検査・provider が契約を実装する必要があり、
方針の式があるだけで全配置の実装保証にはならない。
Datalog による認可も、コンパイラの健全性を証明するものではない。

## 再帰、有限の実行、停止性

Kotoba は再帰と `loop`/`recur` を受け入れる。現在の契約は、すべてのコンポーネントに
一般的な停止性証明を要求していない。「全プログラムの停止を証明する全域言語」とは
説明できない。

- 理想化した計算モデルの表現力を論じる場合、メモリや資源の仮定を明記する。
  再帰や selfhost の存在だけでは、チューリング完全性の証明にはならない。
- 特定の artifact・入力・target・予算による有限の実行を区別する。入力と状態の領域を
  有限に固定し、すべての遷移に有効な上限を与えれば、その範囲は理論上全探索できる。
  その費用が実用的かは別問題で、上限のない問題の判定にはならない。
- 資源を使い切って止まることと、目的の答えを計算して正常終了することを区別する。

[制限値の正本](../../lang/limits.edn)は、「何をしてよいか」と target ごとの資源予算・
停止方法を分ける。[fuel model](fuel-model.md)には次の条件がある。

- reference・Wasm・制限された JavaScript のプロファイルには、既定で512の呼び出し fuel
  がある。これは命令数や実時間の予算ではない。
- 合成された loop helper は、記録された KIR/Wasm 経路で自己末尾再入時に課金しない。
  有限の呼び出し fuel だけでは、この反復を制限できない。
- POSIX native kexe のプロファイルでは、決定的な fuel 計測が既定で無効である。
  CPU時間・実時間の緊急停止は言語の意味の外にある。
  計測を維持する別の native プロファイルは `lang/limits.edn` が列挙する。
- provider の所要時間、メモリ、出力、命令による中断には、それぞれの制限が必要である。
  選んだホストが実際にその機構を提供・強制していることも確認する。

資源エラーや強制終了は、元のアルゴリズムが正常に停止する証拠ではない。
「fuel によってすべての Kotoba プログラムの停止を証明している」という主張は、
現在の契約を超える。

## CID と意味的同値性

[typed-eval 契約](../../lang/typed-eval.edn)は、DefCID、AdmissionCID、ValueCID を分ける。
それぞれ選んだ定義、受け入れた実行文脈、得られた値を識別する。
正規化と内容に基づく識別は、規定された範囲での比較や再現に役立つが、任意の二つの
プログラムが同じ関数を計算するかを判定するものではない。
異なる定義が同じ関数を計算することも、識別・署名された定義に論理バグがあることもある。

## 根拠と更新条件

この解説はソースを読んだ評価であり、新しい runtime 試験や本番環境の実行保証ではない。
仕様の確認時点は `kotoba-lang/kotoba-lang@1e535060ddfd989fd4866a44b38eea440e03ee67`。
作業中の未コミット変更と分けて確認した実装の固定リビジョン、理論の出典は
[英語正本の根拠](computability-and-safety.md#evidence-and-maintenance)に記録する。
互換実装を含むソース上の観察を、selfhost/native 全体の検証済みという主張に広げない。

effect 推論、再帰、計測、ホストの停止機構、値の上限、内容識別の意味が変わったら
この文書を見直す。日付つきの解説よりも、各所有リポジトリの現在の契約を優先する。
